## Couches d'authentification

Reelevant sépare l'authentification en couches distinctes :

| Couche | Mécanisme | Quand il s'applique |
|--------|-----------|---------------------|
| **Intégration de Content** | URL publiques — pas d'authentification | Requêtes Runner (`reelevant.run`) |
| **Accès plateforme** | Email/mot de passe ou SSO | Tableau de bord (`app.reelevant.com`) |
| **API plateforme** | Tokens Bearer OAuth 2.0 | Accès programmatique à toutes les capacités de la plateforme |
| **Provisionnement d'annuaire** | Jeton bearer SCIM 2.0 | Provisionnement des comptes et des groupes piloté par votre IdP |

## Intégration de Content (publique)

Les URL d'intégration — balises image, liens de redirection et endpoints Runner — sont **accessibles publiquement**. Aucun en-tête d'authentification ou token n'est requis au moment de la requête.

Les identifiants client sont transmis en tant que **paramètres de requête URL** (ex. : `uid`, `rlvt-u`). Ils sont publics par conception : ils apparaissent dans le code source HTML des emails, l'historique du navigateur et les logs des proxys. Utilisez des identifiants client opaques plutôt que des adresses email ou d'autres données personnelles.

## Accès à la plateforme

### Email et mot de passe

Connexion standard sur [app.reelevant.com](https://app.reelevant.com). Les utilisateurs s'authentifient avec leur adresse email et leur mot de passe. L'authentification multi-facteurs (MFA) est supportée.

### Single Sign-On (SSO)

Reelevant supporte l'intégration SSO avec le fournisseur d'identité de votre organisation. Lorsque le SSO est configuré, les utilisateurs sont automatiquement redirigés vers votre IdP pour l'authentification — aucun mot de passe Reelevant séparé n'est requis.

**Protocole supporté :**
- **SAML 2.0** — Protocole SSO standard pour entreprises

**La configuration SSO inclut :**

| Paramètre | Description |
|-----------|-------------|
| URL du fournisseur d'identité | L'endpoint SSO de votre IdP |
| Entity ID | L'identifiant de Reelevant dans votre IdP |
| Certificat | Certificat X.509 pour la vérification de confiance entre Reelevant et votre IdP |
| Mapping d'attributs | Associez les attributs utilisateur de l'IdP aux champs utilisateur Reelevant |
| Rôle par défaut | Rôle attribué aux utilisateurs créés via la plateforme |

**Provisionnement des utilisateurs :**

Deux modes de provisionnement sont disponibles, et ils peuvent être combinés :

| Mode | Comportement |
|------|--------------|
| **Invitation** (par défaut) | L'utilisateur doit déjà disposer d'un compte Reelevant, ou d'une invitation en attente, correspondant à son identité IdP |
| **Just-in-time (JIT)** | Le compte est créé à la première assertion SAML valide, avec le rôle et les Teams par défaut de la société, et les champs de profil issus des attributs d'assertion mappés |

<Info>
La configuration SSO est gérée au niveau de l'organisation. Contactez votre équipe de compte Reelevant ou support@reelevant.com pour activer et configurer le SSO pour votre organisation.
</Info>

### Provisionnement SCIM 2.0

Reelevant expose un service provider **SCIM 2.0** entrant : votre IdP (Entra ID, Okta, Ping, ou tout client SCIM 2.0) devient la source de vérité des comptes. SCIM se configure indépendamment du SSO — vous pouvez provisionner via SCIM tout en conservant la connexion par mot de passe, ou l'inverse.

| Capacité | Support |
|----------|---------|
| Ressources | `/Users` et `/Groups` — création, lecture, remplacement (`PUT`), modification partielle (`PATCH`), suppression |
| Découverte | `/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas` |
| Authentification | Un jeton bearer SCIM propre à la société ; le tenant est toujours déduit du jeton, jamais d'une valeur envoyée par l'IdP |
| Gestion des jetons | Jusqu'à deux jetons actifs simultanément pour permettre la rotation sans interrompre l'IdP ; le secret n'est affiché qu'une fois, stocké haché, et révocable |
| Désactivation | `active: false` désactive immédiatement le compte : toutes les voies d'authentification sont fermées et les sessions existantes révoquées. Le repasser à `true` restaure le même rôle et les mêmes Teams |
| Déprovisionnement | Configurable par société : `soft` (le `DELETE` désactive le compte, comportement par défaut) ou `hard` (le compte et ses dépendances sont effacés) |
| Synchronisation des groupes | Les Groups SCIM sont associés aux Teams Reelevant, ce qui maintient le cloisonnement des ressources aligné sur votre annuaire |
| Attribution des rôles | Depuis l'attribut SCIM `roles`, ou depuis l'appartenance aux groupes via un mapping groupe → rôle que vous définissez ; une valeur non résolue retombe sur un rôle par défaut configurable au lieu de faire échouer l'opération |
| Mapping d'attributs | `userName`, `externalId`, `active`, `name.givenName` / `familyName`, `title`, `phoneNumbers`, `preferredLanguage`, `roles`, `groups` |
| Filtres et pagination | Filtres `eq` simples et `startIndex` / `count`, jusqu'à 200 résultats par page |
| Non supporté | Opérations bulk, `/Me`, tri, ETags, et changement de mot de passe via SCIM |
| Traçabilité | Chaque opération de provisionnement est enregistrée dans le [journal d'audit](/fr/why-reelevant/technical-evaluators/security), attribuée au jeton SCIM qui l'a exécutée |

Les comptes de service ne sont jamais touchés par SCIM : ils sont gérés dans Reelevant, de sorte qu'une synchronisation IdP ne peut pas désactiver les identités machine dont dépendent vos intégrations. Un compte créé auparavant par invitation ou par JIT SSO est repris en place au premier appel SCIM correspondant, plutôt que dupliqué.

<Info>
L'activation de SCIM fournit l'URL de base à configurer dans votre IdP ainsi que le jeton bearer. Contactez votre équipe de compte Reelevant ou support@reelevant.com pour l'activer.
</Info>

## Modèle d'autorisation

Une fois authentifié, l'accès est contrôlé via **RBAC** et **ABAC** :

### RBAC (contrôle d'accès basé sur les rôles)

Chaque utilisateur se voit attribuer un [rôle](/fr/product-guide/account/roles) qui définit les actions autorisées sur les types de ressources :

| Ressource | Actions |
|-----------|---------|
| Workflows | Créer, lire, mettre à jour, supprimer, publier |
| Contents | Créer, lire, mettre à jour, supprimer |
| Datasources | Créer, lire, mettre à jour, supprimer, configurer |
| Analytics | Lire, exporter |
| Rôles | Créer, lire, mettre à jour, supprimer |
| Teams | Créer, lire, mettre à jour, supprimer, assigner des membres |
| Paramètres | Lire, mettre à jour |

### ABAC (contrôle d'accès basé sur les attributs)

Les permissions sont affinées par des attributs :

- **Entreprise** — L'isolation par tenant garantit que les utilisateurs n'accèdent qu'aux ressources de leur organisation
- **Team** — Les ressources sont assignées à des Teams ; les utilisateurs ne voient que les ressources appartenant à leurs Teams

Cela signifie qu'un utilisateur avec le rôle « Editor » dans « Team Marketing » peut modifier les Workflows assignés à cette Team, mais ne peut pas voir ou modifier les Workflows appartenant à « Team CRM ».

Voir [Permissions](/fr/product-guide/account/permissions) pour le modèle d'accès complet.

## Authentification API

### API de la plateforme

Reelevant traite ses API comme des citoyens de première classe au même titre que l'interface. Toutes les capacités de la plateforme sont accessibles programmatiquement via des API REST :

- **Tokens Bearer OAuth 2.0** pour l'authentification
- Les tokens sont scopés par environnement (staging / production)
- Les tokens sont gérés dans la plateforme sous les paramètres du compte
- Toutes les requêtes API nécessitent l'en-tête `Authorization: Bearer {token}`

Voir [Authentification API](/fr/developer-docs/api-reference/authentication) pour les flux OAuth 2.0 et la gestion des tokens, et la [référence API](/fr/developer-docs/api-reference/introduction) pour la documentation complète des endpoints.
