## Authentication Layers

Reelevant separates authentication into distinct layers:

| Layer | Mechanism | When it applies |
|-------|-----------|-----------------|
| **Content integration** | Public URLs — no auth | Runner requests (`reelevant.run`) |
| **Platform access** | Email/password or SSO | Dashboard (`app.reelevant.com`) |
| **Platform APIs** | OAuth 2.0 Bearer tokens | Programmatic access to all platform capabilities |
| **Directory provisioning** | SCIM 2.0 bearer token | Account and group provisioning driven by your IdP |

## Content Integration (Public)

Integration URLs — image tags, redirection links, and Runner endpoints — are **publicly accessible**. No authentication header or token is required at request time.

Customer identifiers are passed as **URL query parameters** (e.g. `uid`, `rlvt-u`). These are public by design: they appear in email HTML source, browser history, and proxy logs. Use opaque customer IDs rather than email addresses or other PII.

## Platform Access

### Email and Password

Standard login at [app.reelevant.com](https://app.reelevant.com). Users authenticate with their email address and password. Multi-factor authentication (MFA) is supported.

### Single Sign-On (SSO)

Reelevant supports SSO integration with your organisation's identity provider. When SSO is configured, users are automatically redirected to your IdP for authentication — no separate Reelevant password is required.

**Supported protocol:**
- **SAML 2.0** — Standard enterprise SSO protocol

**SSO configuration includes:**

| Setting | Description |
|---------|-------------|
| Identity Provider URL | Your IdP's SSO endpoint |
| Entity ID | Reelevant's identifier in your IdP |
| Certificate | X.509 certificate for trust verification between Reelevant and your IdP |
| Attribute mapping | Map IdP user attributes to Reelevant user fields |
| Default role | Role assigned to users created via the platform |

**User provisioning:**

Two provisioning modes are available, and they can be combined:

| Mode | Behaviour |
|------|-----------|
| **Invitation** (default) | The user must already have a Reelevant account, or a pending invitation, matching their IdP identity |
| **Just-in-time (JIT)** | The account is created on the first valid SAML assertion, with the company's default role and Teams, and the profile fields taken from the mapped assertion attributes |

<Info>
SSO configuration is managed at the organisation level. Contact your Reelevant account team or support@reelevant.com to enable and configure SSO for your organisation.
</Info>

### SCIM 2.0 Provisioning

Reelevant exposes an inbound **SCIM 2.0** service provider, so your IdP (Entra ID, Okta, Ping, or any SCIM 2.0 client) becomes the source of truth for accounts. SCIM is configured independently of SSO — you can provision with SCIM while still using password login, or the reverse.

| Capability | Support |
|------------|---------|
| Resources | `/Users` and `/Groups` — create, read, replace (`PUT`), patch (`PATCH`), delete |
| Discovery | `/ServiceProviderConfig`, `/ResourceTypes`, `/Schemas` |
| Authentication | A company-scoped SCIM bearer token; the tenant is always derived from the token, never from a value sent by the IdP |
| Token management | Up to two active tokens at a time so you can rotate without interrupting the IdP; the secret is shown once, stored hashed, and revocable |
| Deactivation | `active: false` disables the account immediately: every authentication path is closed and existing sessions are revoked. Setting it back to `true` restores the same role and Teams |
| Deprovisioning | Configurable per company: `soft` (`DELETE` disables the account, the default) or `hard` (the account and its dependents are erased) |
| Group synchronisation | SCIM Groups map to Reelevant Teams, keeping resource scoping aligned with your directory |
| Role assignment | From the SCIM `roles` attribute, or from group membership through a group-to-role mapping you define; unresolved values fall back to a configurable default role instead of failing the operation |
| Attribute mapping | `userName`, `externalId`, `active`, `name.givenName` / `familyName`, `title`, `phoneNumbers`, `preferredLanguage`, `roles`, `groups` |
| Filtering and pagination | Simple `eq` filters and `startIndex` / `count`, up to 200 results per page |
| Not supported | Bulk operations, `/Me`, sorting, ETags, and password changes over SCIM |
| Auditing | Every provisioning operation is recorded in the [audit log](/why-reelevant/technical-evaluators/security), attributed to the SCIM token that performed it |

Service accounts are never touched by SCIM: they are managed inside Reelevant, so an IdP sync cannot disable the machine identities your integrations rely on. An account previously created through an invitation or SSO JIT is adopted in place on the first matching SCIM call rather than duplicated.

<Info>
Enabling SCIM returns the base URL to configure in your IdP together with the bearer token. Contact your Reelevant account team or support@reelevant.com to activate it.
</Info>

## Authorisation Model

Once authenticated, access is enforced through **RBAC** and **ABAC**:

### RBAC (Role-Based Access Control)

Each user is assigned a [role](/product-guide/account/roles) that defines permitted actions on resource types:

| Resource | Actions |
|----------|---------|
| Workflows | Create, read, update, delete, publish |
| Contents | Create, read, update, delete |
| Datasources | Create, read, update, delete, configure |
| Analytics | Read, export |
| Roles | Create, read, update, delete |
| Teams | Create, read, update, delete, assign members |
| Settings | Read, update |

### ABAC (Attribute-Based Access Control)

Permissions are further scoped by attributes:

- **Company** — Tenant isolation ensures users only access their organisation's resources
- **Team** — Resources are assigned to Teams; users only see resources belonging to their Teams

This means a user with the "Editor" role in "Team Marketing" can edit Workflows assigned to that team, but cannot see or modify Workflows belonging to "Team CRM".

See [Permissions](/product-guide/account/permissions) for the full access model.

## API Authentication

### Platform APIs

Reelevant treats its APIs as first-class citizens alongside the UI. All platform capabilities are accessible programmatically via REST APIs:

- **OAuth 2.0 Bearer tokens** for authentication
- Tokens are scoped per environment (staging / production)
- Tokens are managed in the platform under Account settings
- All API requests require the `Authorization: Bearer {token}` header

See [API Authentication](/developer-docs/api-reference/authentication) for OAuth 2.0 flows and token management, and the [API Reference](/developer-docs/api-reference/introduction) for full endpoint documentation.
